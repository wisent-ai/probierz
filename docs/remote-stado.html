Remote execution on Stado

The Stado bridge runs a Probierz target, an authoring round, or the SEO evaluator on explicitly selected Stado capacity and brings the evidence back into the local test-results/ tree, so history, status, and the gate treat remote runs like local ones. Selecting a host grants exactly one job on that capacity, nothing broader; an unavailable fleet is reported as unavailable, not as empty or successful.

Host selectors

probierz hosts lists the run hosts. local is this machine (the default for plain probierz run). The stado:* selectors submit to the Stado queue:

| Selector | Capacity | |---|---| | stado:gcp / stado:azure / stado:aws | provider-pinned consumers | | stado:any | any consumer with capacity | | stado:spot | cost-capped capacity | | stado:local | local-kind consumers | | stado:mini / stado:macbook | dedicated macOS consumers | | stado:t4 | nvidia-tesla-t4 GPU capacity |

How a remote job works

The private Probierz checkout travels as a tarball through stado://probierz/inputs, together with a generated job script and any application inputs. The worker unpacks the checkout, provisions the application, runs the same node agent/cli.mjs run <target> contract (with PROBIERZ_RUN_KIND=pull-request), archives test-results/ — even for a failing run — into stado://probierz/results, and exits with the run's own status. probierz stado run then downloads and unpacks the evidence under test-results/.remote/<jobId>/ and into the normal evidence tree. A failed job's retained artifacts are fetched too, including a blocked preflight, so a remote failure stays diagnosable. --no-watch submits without waiting.

Application provisioning is explicit per invocation:

  • `--cargo-release --app-repo <path> --binary <name>

[--cargo-manifest <path>]` — pack the application repository, build it with a Rust release build on the worker.

  • --app-bundle-path <path> --app-repo <path> — ship a prebuilt macOS app

bundle plus its source for identity.

  • `--node-source --app-repo <path> [--env K=V ...]

[--script apps/<id>/remote/x.sh]` — pack a JS application's source; an optional repo-committed script replaces the default run command.

Remote runs accept repeated --env NAME=VALUE (or --env=NAME=VALUE) for non-secret run conditions, whether the application is provisioned or already installed. The application archive contains the same Git-listed source files measured for the source identity, not ignored build output. Source-provisioned workers receive PROBIERZ_APP_SOURCE, PROBIERZ_TOOLKIT_ROOT, and the submitter's recorded source identity.

Recover an interrupted watch

Submission requests and responses remain under test-results/.remote/. Before watching, stderr prints the request receipt and the accepted job ID. probierz stado collect <job-id> --app <app-id> --host stado:mini downloads a terminal job's retained reports and artifacts without submitting or running it again. The MCP command is probierz_stado_collect. A running job is reported as running, not as passed; a failed run keeps its failed verdict after collection.

probierz stado collect returns immediately when the existing job is still queued or running. To wait for that same job, use probierz stado resume <job-id> --host stado:mini, or probierz_stado_resume over MCP. The wait uses the original run's saved budget, derived from its selected journeys and setup steps; it never creates a replacement job. Both commands import the original retained evidence rather than manufacturing a new run.

Native GUI readiness is a multi-step Stado audit with a separate 30-minute deadline. If that deadline expires, the report says that readiness is unknown and no GUI job was submitted; it does not claim that the host is down. Permission grants and system consent are not part of this preflight.

Secrets

Remote jobs never embed credentials in the payload. The job declares secret references — for example the probierz-model-router / token reference for STADO_MODEL_ROUTER_TOKEN — and Stado materializes them on the worker. Locally, the bridge shells out to the installed stado CLI (stado storage put/get, stado machine submit/status/artifacts), so Stado's own configuration applies; a host selector may override STADO_API_URL for its jobs. See configuration.

Remote authoring and SEO

  • probierz stado author <appId> <journey> --target <t> --desc <d> [--area <name>] [--host h] runs the product-owned authoring loop on a Stado host with scoped model and product credentials.

The job carries the submitting source and its identity, and returns only retained reports plus receipt-bound accepted bytes and relative metadata. The submitter verifies the green run, source, paths, byte count and hash, then writes tests/<area>/<journey>.probierz.spec.* in the exact original checkout and recreates the toolkit registration as a relative symlink. A per-job source receipt lets stado collect or stado resume finish interrupted collection without deleting earlier reports; worker-local product paths and manifests are never installed.

  • `probierz stado seo <appId> --base-url <url> --primary-model <id>

--secondary-model <id> --adjudicator-model <id> [--mode ...] [--host stado:mini] runs the complete SEO evaluator on a dedicated host, materializing only the declared router bearer, agent secret, and — when the profile requires signing — the SEO receipt key. No secret enters argv`.
